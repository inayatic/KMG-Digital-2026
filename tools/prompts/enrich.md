# Промпт «enrich»: заполнить пробелы слоя по схеме организаторов
Подставляется: CHAPTER (latyshova), KEY (раздел).
Вход: build/CHAPTER/org/in/KEY.json (компактные узлы раздела). Подробности при необходимости: build/CHAPTER/sections/<KEY>/units.json и nodes.json, сканы PDF. Схема: reference/organizers/01_схемы/node.schema.json и routing.schema.json (читать, не править). Типы трудности и форматы подачи: reference/organizers/06_подача_и_референсы/подача_доменов_геологии.md (строки про типы М, В, И, Ф, П, Пр, Н, Р — таблица «Тип / Что должен построить человек / Ведущий формат»).

ВАЖНО: поле legacy_difficulty_unverified — буквы, расставленные раньше по ДОГАДКЕ с неверной трактовкой (П читали как «понятие», В как «визуализацию», Н как «нюансы», Р как «расчёт»). Не доверяй им. Расставь тип трудности заново по определениям организаторов: М — механизм процесса; В — геологическое время; И — косвенное измерение (сигнал→отклик→свойство, ответов может быть несколько); Ф — формализм и модель (смысл уравнения); П — пространство (объём по картам и разрезам); Пр — процедура (порядок действий, входные данные, точки выбора, ручной труд); Н — неопределённость и решение (диапазон вместо числа, цена ошибки); Р — распознавание (узнать признак на фото/кривой). primary — что ГЛАВНОЕ трудно понять в узле; secondary — второй тип или null.

Для КАЖДОГО узла раздела запиши патч (только эти поля, остальное не трогай):
- id;
- difficulty: {primary, secondary};
- threshold: true/false (пороговая идея: после неё предмет виден иначе; обычно false, true редко и только если узел реально такой);
- terms_introduced: термины, которые узел впервые объясняет (по тексту утверждений; термины автора, 0–6);
- terms_used: термины, которые узел использует, но не объясняет (0–6);
- main: 1–2 фразы «главная мысль узла» своими словами строго по claims узла (без новых фактов);
- breaks: что ломается/ограничения/условия применимости — только то, что следует из claims, layers.nuances или условий автора; если книга ничего не говорит, пиши «книга условий не называет» (не выдумывай);
- hypotheses: список гипотез о значении для данных (обычно []); каждая явно «гипотеза»;
- it_analogy: ТОЛЬКО если в узле analogy пусто и есть честная ИТ-аналогия: {text, breaks_where}; иначе null (пустое лучше выдуманного);
- video_scores: {time, invisible, scale, counterintuitive, cause_effect}, каждый 0–2 (критерии видеоёмкости: изменение во времени; невидимое становится видимым; скачок масштаба; контринтуитивность; причина и следствие), оценка по содержанию узла;
- secondary_format: формат из списка схемы маршрутизации или null; route_why: 1–2 фразы обоснования формата по типу трудности и видеоёмкости, согласованные с форматом route.format (если считаешь формат неверным, дай новый route_format с обоснованием).
Правила: не добавляй фактов вне claims узла; не вводи заблуждения; всё, что пишешь, — работа модели (by_model). Не правь исходные файлы.
Выход: ТОЛЬКО build/CHAPTER/org/patches/KEY.json — список патчей по одному на каждый узел раздела (все id из in/KEY.json). Проверь, что JSON валиден и id совпадают. Рабочие файлы в /tmp/claude-0/ewk-KEY/.
Отчёт ≤6 строк: узлов, распределение primary, сколько пороговых, сколько analogy добавлено.
